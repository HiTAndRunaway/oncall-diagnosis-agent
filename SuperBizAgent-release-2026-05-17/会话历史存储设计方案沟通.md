# 会话历史存储设计方案 — 沟通记录

**日期**: 2026-07-03 ~ 2026-07-04
**主题**: 将 ChatController 中的 ConcurrentHashMap 会话存储迁移至 Redis

---

## 需求背景

用户提出：当前项目的对话 Agent 使用 `ConcurrentHashMap` 实现会话记忆，每个用户的会话记忆都存在 map 中。希望改造成使用 Redis 来存储会话记忆。

## 问答过程

### Q1: Redis 部署方式

**问题**: 对 Redis 的部署方式有什么偏好？

**选项**:
- A) 独立 Redis（推荐）— 在现有 vector-database.yml 旁边加一个 redis 容器，应用直连 Redis
- B) Spring Session Redis — 引入 spring-session-data-redis，把整个 HTTP Session 托管给 Redis
- C) 仅用本地 Redis — 开发/测试阶段本机装 Redis，不容器化

**用户选择**: A — 独立 Redis

---

### Q2: 会话过期时间（TTL）

**问题**: 会话数据要不要设过期时间（TTL）？

当前 ConcurrentHashMap 里的会话是永久存储的，除非用户手动调 `/chat/clear` 清掉，否则永远不删。

**选项**:
- A) 设 TTL 自动过期（推荐）— 比如 24 小时无访问自动删除
- B) 不设过期，保持现状
- C) 可配置 — 在 application.yml 里配一个 session.ttl-hours，默认 24h，设为 0 表示永不过期

**用户选择**: C — 可配置，默认 24h 过期

---

### Q3: sessionId 返回机制

**问题**: 当前如果客户端没传 sessionId，后端会生成一个 UUID，但不会把生成的 sessionId 返回给客户端。换成 Redis 后，客户端下次对话如果还拿不到这个 sessionId，就永远找不回之前的会话。

**选项**:
- A) 顺带修复（推荐）— 在 API 响应里加上 sessionId 字段，让前端可以存下来，后续请求带上
- B) 保持现状 — 前端必须自己在首次请求前就生成好 sessionId 传过来（目前前端已经是这么做的）

**用户选择**: A — 后端返回时需要加上会话 id 字段，后续前端每次请求时需要带上对应的会话 id

---

### Q4: Redis 数据结构

**问题**: 会话数据用 Redis 存的时候，倾向哪种数据结构？

**选项**:
- A) JSON 字符串（推荐）— 每个 session 一个 key，value 是一个 JSON 序列化的对象
- B) Redis Hash — 元数据放 Hash field，消息列表单独放
- C) Redis List — 消息用 List 逐条 push，元数据用 Hash

**用户选择**: A — 每个 session 都是一个 key，对应的 value 值使用 JSON 存储

---

### Q5: 消息历史存储粒度 — 是否需要摘要层

**问题**: 消息历史的存储粒度。当前方案把历史消息拼进系统提示词，靠 LLM 自己理解上下文。历史消息太长会吃掉大量 token。是否考虑用 Redis 做上下文摘要？

**选项**:
- A) 保持现状 — Redis 存原始消息列表，仍然拼到 system prompt
- B) 加摘要层 — 存最近 N 对原始消息 + 一个早期历史的 AI 生成摘要

**用户选择**: B — 希望做到每个 sessionId 对应的会话历史如果太长（超过配置的长度）就异步调用 LLM 来给对话历史生成摘要。Redis 中摘要层的形式是 `<sessionId, 对话摘要>`。如果没找到对话摘要再去找详细的对话历史层，如果对话历史层也没找到就是一个新的会话。

---

### Q6: 摘要开关可配置

**用户补充需求**: 希望在 yml 文件里边加一个可配置项，用于配置是否查 Redis 中的摘要层。配置的值如果是 true 就查摘要，false 就跳过摘要直接查对话历史层。

**确认**: 已纳入配置设计。

## 最终设计方案要点

### 架构

- 新建 `SessionManager` Service，替代 ConcurrentHashMap
- 新建 `SummaryGenerator` Service，异步调用 LLM 生成摘要
- ChatController 去掉 SessionInfo 内部类，注入 SessionManager
- 新增 Redis 容器（redis:7-alpine），加在 vector-database.yml

### Redis 三层 Key

| 层 | Key 格式 | 说明 |
|---|---|---|
| 摘要层 | `session:{id}:summary` | LLM 生成的对话摘要 JSON |
| 详情层 | `session:{id}:history` | 原始消息列表 JSON |
| 元数据 | `session:{id}:meta` | 创建时间、消息对数等 |

### 读写路径

- **读**: 先查摘要层 → 未命中或关闭则查详情层 → 都未命中则为新会话
- **写**: 追加到详情层 → 更新元数据 → 刷新 TTL → 超过阈值则异步生成摘要
- **摘要生成后**: 写入摘要层，详情层保留不删除（摘要和详情共存）

### 配置项

```yaml
session:
  redis:
    ttl-hours: 24
    summary:
      enabled: true
      trigger-threshold: 10
      model: "qwen3-max"
      max-summary-length: 500
```

### 响应格式变更

- `/api/chat` 响应新增 `sessionId` 字段
- `/api/chat_stream` SSE done 事件新增 `sessionId` 字段
- 前端从响应中读取 sessionId 并存储

### 文件变更

- **新建**: SessionManager.java, SummaryGenerator.java, RedisConfig.java
- **修改**: ChatController.java, ChatService.java, pom.xml, application.yml, vector-database.yml, Makefile, app.js

## 设计方案修订记录

### 修订 1（2026-07-04）: 摘要层和详情层共存

**用户反馈**: 设计方案中"摘要生成后删除详情层"不合理。会话历史被摘要后，原本的详细会话历史不要删除。

**修改内容**:

| 位置 | 原设计 | 修订后 |
|---|---|---|
| §3 数据模型规则 | 摘要和详情互斥，摘要生成后删除详情层 | 摘要和详情**共存**，详情层始终保留 |
| §4 添加消息路径 | 步骤 d: 删除 session:{id}:history | 步骤 d: 更新 meta，记录摘要生成时间 |
| §6 异步摘要生成 | 步骤 5: 删除 session:{id}:history | 步骤 5: 更新 meta，记录摘要时间戳 |
| §10 边界情况 | "摘要完成后仅删除生成时的消息" | 新增一行：摘要多次生成时覆盖旧摘要，详情层始终保留 |

**修订后的核心逻辑**:
- 摘要层和详情层各自独立存在，各自有 TTL
- 读取时：摘要优先（节省 token），详情层作为完整记录保留
- 摘要可被覆盖（消息继续增长超过阈值时重新生成），详情层永远不被摘要流程删除
- 详情层的存在也便于后续调试或重新生成摘要时使用完整历史
